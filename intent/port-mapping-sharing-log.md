# DSH Terminal Manager — 端口映射、会话共享与日志增量

- 作者：产品负责人 / Codex 协作整理
- 来源：2026-09-01 IDE 会话；参考 `ipop-port-mapping-sharing-log-design.md`
- 状态：Draft
- 日期：2026-09-01

## 问题

当前 DSH Terminal Manager 已能集中管理 SSH/Telnet 会话，但仍缺少三类与终端运维紧密相关的本地能力：

1. 不能在 DSH 内配置并运行 TCP/UDP 本地端口转发，只能依赖外部转发工具；
2. 不能把某个正在运行的终端会话实时共享给其他本地或局域网客户端观看/协作；
3. 缺少可轮转的插件运行日志和按会话启停的终端输出日志，故障定位与操作留存不便。

IPOP 文档提供了功能语义和已知缺陷清单，但其 C++/Electron 实现不能直接移植。新功能必须复用当前插件的公共会话池、控制面、数据面、持久化目录和 UI 工作区，以增量方式加入，不能形成第二套应用或改变现有终端行为。

## 期望结果

交付完成后，用户可以在现有 DSH 插件工作区内完成以下可观察操作：

1. 创建、编辑、删除、启动和停止 TCP/UDP 端口映射；配置持久化，可选择随插件启动；UI 能看到运行状态、最近错误、活跃连接/会话数和收发字节数；TCP 与 UDP 均有本地端到端测试证明双向转发有效。
2. 对任一已打开的 SSH/Telnet 会话启动和停止 TCP 会话共享；多个客户端可实时收到同一份会话输出；只读模式下客户端输入不会到达设备，可写模式下输入复用现有 `SessionManager.write` 路径；会话关闭或插件卸载时共享端口和客户端全部被清理。
3. 生成插件运行日志和会话输出日志。运行日志支持级别、大小/数量轮转；会话日志默认关闭、可按会话启停，可选时间戳和 ANSI 清理，UI 展示当前状态及文件路径；所有日志都不得记录密码、私钥或认证载荷。
4. 上述能力通过现有 `/term-manager` 控制面和必要的数据订阅接入现有 React 工作区，沿用当前交互语言、DSH 设计 token、`.tm-` 样式前缀和错误格式，不破坏连接管理、多终端显示、人工输入或 AI 工具。
5. `pnpm build`、既有测试和新增单元/集成测试全部通过；Socket 生命周期、端口冲突、IPv4/IPv6、UDP 源端点隔离、慢客户端背压、日志轮转与敏感信息过滤都有回归证据。

## 受影响的用户与系统

- 用户：当前 DSH Terminal Manager 的本机/小团队使用者，以及经授权连接共享端口的观察者或协作者。
- Host 半：`src/index.ts` 装配与卸载、`SessionManager` 输出订阅/人工写入、`/term-manager` 控制面、配置持久化、Node.js TCP/UDP 与文件系统能力。
- 浏览器半：现有终端工作区、终端窗格操作区、RPC 客户端与集中式 `client/styles.ts`。
- 数据：继续以 `resolveDataDir()` 为根目录，新增映射配置、日志配置和日志子目录；不得改写现有 `connections.json` 的语义。
- 决策人：用户本人（产品负责人）；涉及对外监听、远程输入和日志内容的安全默认值需由其明确批准。

## 约束

- 仅做当前 Cordis/DSH 插件的增量开发，不修改 DSH 核心，不创建独立 app 或外部中间服务。
- Host 与浏览器实现保持 TypeScript strict；前端保持 React 18；样式继续集中在 `client/styles.ts`，使用 `.tm-` 前缀和现有 `--dsw-*` token，不引入另一套组件库或 CSS Modules。
- 复用现有 `SessionManager` 作为终端输出和输入的唯一接缝；端口共享不得直接接触 SSH/Telnet transport。
- 复用 `/term-manager` 与既有路由注册/清理方式；浏览器不可直接操作本机 Socket 或文件系统。
- 采用 Node.js 事件驱动 I/O，不照搬 IPOP 的线程、busy-loop、手工内存或 C++ Socket 代码；IPOP 已列出的删除、IPv6、UDP、资源泄漏和关闭竞态缺陷必须有针对性测试。
- 默认配置必须安全：不自动暴露公网监听、不默认允许共享客户端写入、会话日志默认关闭、错误与日志不含凭据。任何放宽必须在 UI 中清晰显示风险。
- 保留现有连接配置和会话行为的向后兼容；插件卸载必须通过 `ctx.effect` 完成映射、共享、日志流和会话的确定性清理。
- Windows 是当前必验平台；Socket 与路径实现尽量使用 Node.js 跨平台 API，避免写死盘符或仅 Windows 可用的调用。

## 范围外

- SSH 隧道、反向隧道、SOCKS 代理；本次端口映射是独立于 SSH 的纯 TCP/UDP 转发。
- 云端中继、NAT 穿透、公网发现、账号体系、多人房间、语音/文件协作。
- 串口、FTP/SFTP、文件传输及从远端设备拉取日志文件。
- 日志全文检索、结构化分析、审计报表、回放引擎或上传到外部日志平台。
- 修改 DSH 核心认证、权限模型或部署流程。

## 开放问题

1. **共享监听与认证**：建议 MVP 默认 `127.0.0.1`、只读；允许用户显式选择局域网地址。若允许 `0.0.0.0` 或远程可写，共享端口是否必须增加一次性访问令牌/口令？
2. **会话日志内容**：建议只记录设备输出，不记录用户/共享客户端输入，以降低密码泄漏风险。是否确实需要记录输入；若需要，密码提示阶段如何脱敏？
3. **功能控制面**：建议首版仅提供 GUI/RPC，不新增可由 DSH Agent 自动开放监听端口、共享会话或读取日志文件的 AI 工具。是否需要 Agent 操作其中某些能力？
4. **端口映射辅助能力**：CSV 导入/导出和完整列表排序是否属于首版验收，还是在核心 TCP/UDP 转发稳定后作为下一增量？
5. **日志保留默认值**：建议应用日志 5 MiB × 5 个文件；会话日志同样需要大小/数量上限，建议每会话 20 MiB、最多保留 20 个文件。是否接受？
