# MVP 演示方案（2026-08-31 · 芯片验证团队对齐）

## 演示定位

**主题**：DSH + dsh-terminal-manager —— 让 Agent 成为芯片验证工程师的"第二双手"

**核心叙事**（贯穿全场）：
```
连接环境 → 读取本地相关内容 → 环境交互
```

**受众**：芯片验证团队（熟悉 SSH/Telnet、命令行、设备调试，对 Agent 能力有好奇但需要看到具体场景）

**时长**：25–30 分钟（含 Q&A）

---

## 前置准备（演示前 30 分钟）

### 1. 启动模拟设备
```bash
# 两个窗口，分别起两台模拟路由器
cd D:/myProject/dsh/dsh-terminal-manager
node scripts/mock-device.mjs 2323   # 设备 A
node scripts/mock-device.mjs 2324   # 设备 B
```

### 2. 启动 DSH
```bash
cd D:/myProject/dsh/deepseek-harness
pnpm dsh --profile tm-dev --port 4580 --no-open
```

### 3. 浏览器
- 打开 `http://127.0.0.1:4580`，硬刷新（Ctrl+F5）
- 准备一个本地测试脚本（演示"读本地文件"用），比如 `test-plan.md` 写着：
  ```
  验证清单：
  - 连上 DUT 后执行 show version，确认固件版本
  - 执行 show ip interface brief，确认接口 up
  ```

### 4. 检查项
- [ ] `/plugins/dsh-terminal-manager/client.js` 返回 200
- [ ] `tm_*` 工具在 DSH 工具面板可见
- [ ] 侧边栏底部有「🖥️ 终端管理」入口

## 演示脚本（四幕）

### 【第一幕】连接环境 —— 单机 Telnet（3 分钟）

**目标**：展示插件的基本形态 —— 在 DSH 里直连设备、人在 Terminal 面板操作。

**操作**：
1. 点侧边栏「🖥️ 终端管理」→ 工作区打开
2. 右侧连接面板：协议 **Telnet**，名称 `dut-1`，主机 `127.0.0.1`，端口 `2323`，点「保存」
3. 点「连接」→ 左侧终端网格出现一个窗格，显示横幅 `Mock Router :2323` + 提示符 `router>`
4. 在终端窗格里敲 `show version` → 看到 `MockOS Version 1.0.4`
5. **解说**：「这就是人直连设备的界面，和 Putty/MobaXterm 的体验一致，但嵌在 DSH 里，跟 Agent 共享会话。」

**要点**：收藏列表、连接状态点（绿色）、横幅渲染。

---

### 【第二幕】多端口同屏 —— 验证场景核心需求（4 分钟）

**目标**：展示芯片验证团队最关心的「同时看多台设备」能力。

**操作**：
1. 再建一条连接 `dut-2`，端口 `2324`，点连接
2. 终端网格自动变成 1×2 并排（或响应式布局）
3. 拖动聊天和终端之间的分隔条 → 展示响应式布局
4. 在底部**广播栏**输入 `show version`，目标「全部」→ 发送
5. 两台终端同时回显 → **解说**：「一条命令，所有 DUT 同时执行。这是批量验证的基础。」
6. 取消勾选一台，再发 → 展示部分广播
7. **解说**：「实际场景里，你可以同时对着 4 台不同工位的板子发同一个回归命令，Terminal 面板同屏看 4 路输出。」

**要点**：1/2/3 列响应式网格、广播栏、两行布局。

---

### 【第三幕】Agent 读取本地 + 环境交互（10 分钟）⭐ 核心

**目标**：展示「Agent 读本地 skill/文件 → 理解任务 → 自动操作环境」的完整闭环。这是用户原话里「最有价值」的部分。

#### 3.1 Agent 单机任务（3 分钟）
**聊天框输入**：
```
读一下当前目录的 test-plan.md，按照里面的验证清单执行
```

**预期 Agent 行为**：
1. 调 DSH 内置工具读本地 `test-plan.md`
2. 解析出两条验证项
3. 调 `tm_connect` 连 `127.0.0.1:2323`（或复用已开dut-1）
4. 调 `tm_send` 跑 `show version`，提取版本
5. 调 `tm_send` 跑 `show ip interface brief`，检查接口
6. 汇总报告

**观察点**：
- 终端工作区同步显示 Agent 的操作（人机共视）
- Agent 的回复结构化，列出「通过/未通过」

#### 3.2 Agent 批量任务（4 分钟）
**聊天框输入**：
```
把 2323 和 2324 两台 DUT 都跑一遍 show version，对比固件版本是不是一致的
```

**预期 Agent 行为**：
1. 调 `tm_connect` 连两台（或复用已有会话）
2. 调 `tm_send` 或 `tm_send_all` 跑命令
3. 对比两台输出，给出结论

**观察点**：
- 终端窗格同时显示两台设备的输出
- Agent 的对比分析出现在聊天区
- **解说**：「以前工程师开 4 个 Putty 窗口，复制粘贴对比；现在 Agent 自动做。」

#### 3.3 Agent 读现场 + 排障（3 分钟）
**聊天框输入**：
```
连上 2323，告诉我当前屏幕上显示什么？设备是什么状态？
```

**预期 Agent 行为**：
1. 调 `tm_read` 读当前环形缓冲
2. 描述设备横幅、提示符状态

**解说**：「Agent 不只是发命令，它也能'看'屏幕。可以帮你确认设备是不是卡在某个状态、是不是有异常输出。」

---

### 【第四幕】安全护栏 + 异常处理（3 分钟）

**目标**：打消芯片验证团队对 Agent 操作设备的顾虑。

#### 4.1 命令守卫
**聊天框输入**：
```
连上 2323，执行 rm -rf /
```
**预期**：Agent 调 `tm_send` 返回 `COMMAND_BLOCKED`，Agent 告诉你被安全策略拦截。
**解说**：「AI 路径的危险命令会被拦截；人手动在终端敲是不拦的——因为人知道自己在干什么。」

#### 4.2 设备掉线
- 在某个终端窗格里敲 `exit`（模拟设备主动断开）
- 观察：窗格标记已断开，状态点变灰，但历史输出保留
- **解说**：「设备掉了，不丢现场。」

## 演示时的关键话术

**对用户说**（懂技术、关心落地）：
- 「插件是 DSH 的插件形态，装上就有，不引入 MCP 之类的外部中间件」
- 「会话是公共池 —— 人连的，Agent 也能接着用；Agent 连的，人也能接着操作」
- 「数据面走本机 loopback 的 WebSocket，不暴露到网络，安全上最保守的 MVP」
- 「命令守卫只拦 AI 路径，人手敲不拦 —— 因为人知道自己在干什么」

**回应可能的提问**：
- Q：能连真实设备吗？A：SSH（密码/密钥）和 Telnet 都支持，本地模拟设备只是为了演示
- Q：能存多少连接？A：JSON 持久化，数量没硬上限
- Q：广播能发多少台？A：实测 10 台并发下延迟 <100ms（本机），受限于设备处理能力
- Q：Agent 能看到实时屏幕吗？A：`tm_read` 读的是环形缓冲（1MiB），不是实时流；实时流是 Terminal 面板看
- Q：9 月还有什么？A：缓存优化、开发环境集成、端口共享、记忆插件、芯片知识库导入（排期待定）

## 演示失败的应急预案

| 风险 | 应对 |
|---|---|
| 模拟设备起不来 | 备第三台端口 2325；或现场换端口 |
| Agent 不调用 tm_* 工具 | 显式提示：「请用 dsh-terminal-manager 的工具」 |
| 广播不响应 | 检查 WS 连接状态（浏览器 F12 → Network） |
| 终端黑屏 | 硬刷新浏览器（Ctrl+F5） |
| 演示时间不够 | 砍掉第四幕，安全护栏口头说明 |
